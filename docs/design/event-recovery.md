# 이벤트 유실 복구 설계

> 분석: `docs/analysis/event-loss.md`
> 대상 문제: L-1(구독 단절 구간 유실), L-2(복구 전략 부재), L-3(단일 상태 슬롯 유실)

## 요구사항

1. 클라이언트 연결이 끊긴 구간에 발행된 알람이 재연결 후 화면에 반영된다
2. 연결 실패가 관측 가능하고, 재연결이 서버에 부담을 주지 않는다
3. 동시 도착 이벤트가 유실되지 않는다
4. 복구 과정에서 발생하는 중복이 사용자에게 노출되지 않는다

## 방식 선택

유실을 해결하는 방법은 크게 두 갈래였다.

### 대안 A — 브로커를 교체한다

`enableSimpleBroker` 를 `enableStompBrokerRelay` 로 바꾸고 RabbitMQ/ActiveMQ 를 둔다.
외부 브로커는 메시지 보관과 재전달을 지원하므로 L-1 이 브로커 레벨에서 해결된다.

- 장점: 전달 보장이 인프라 책임으로 내려가고, 서버를 여러 대로 늘려도 동작한다
- 단점: 운영 구성요소가 하나 늘어난다. 브로커의 큐·TTL·ack 설정을 이해해야 하고,
  Docker Compose 구성도 커진다. 그리고 **이미 DB 에 저장된 알람을 다시 브로커에도 보관**하게 된다

### 대안 B — DB 를 사실의 원천으로 쓰고 재조회한다 (채택)

알람은 이미 PostgreSQL 에 저장되고 있다.
따라서 브로커에 보관 책임을 주지 않고, **클라이언트가 누락을 감지해 REST 로 재조회**하게 한다.

- 장점: 새 구성요소가 없다. 복구 데이터가 이미 존재하므로 저장을 이중화하지 않는다.
  복구 경로가 평범한 REST 조회라 테스트하기 쉽다
- 단점: 클라이언트가 복구 책임을 진다. 서버는 "놓친 사람에게 다시 보내주는" 역할을 하지 않는다.
  설비 상태 이벤트(`/topic/equipment-status`)는 이력 테이블이 없어 같은 방식을 쓸 수 없다

**채택 근거:** 지금 문제는 "브로커에 전달 보장 기능이 없다"가 아니라
"이미 저장된 데이터를 다시 읽을 경로가 없다"에 가깝다.
저장소가 이미 사실을 보관하고 있으므로, 보관 계층을 하나 더 두기보다 조회 경로를 만드는 쪽이 구조적으로 단순하다.

대안 A 는 서버를 여러 대로 운영하거나 알람 외 이벤트까지 전달 보장이 필요해지는 시점에 다시 검토할 선택지다.
(`enableSimpleBroker` 는 인스턴스 간 전파가 되지 않으므로, 다중 서버에서는 A 가 사실상 필수가 된다.)

## 복구 식별자

클라이언트가 "어디까지 받았는지" 표현할 수단이 필요하다. 세 가지를 검토했다.

| 방식 | 평가 |
|---|---|
| `createdAt` 타임스탬프 | 동일 시각 알람이 여러 건이면 경계가 모호하다. 서버 시계 역행 시 누락 위험 |
| 별도 이벤트 시퀀스 컬럼/테이블 | 이벤트 종류와 무관하게 통일된 순번을 줄 수 있으나, 발급 지점과 경합 처리가 추가된다 |
| **알람 PK(`alarm.id`)** — 채택 | 단조 증가 식별자가 이미 존재한다. 추가 스키마가 없고, 정렬·비교 의미가 명확하다 |

**채택: `alarm.id`**

**명시적 한계:** 이 식별자는 알람 도메인에만 유효하다.
설비 상태 변경 이벤트는 이력을 저장하지 않으므로 같은 방식으로 복구할 수 없다.
설비 상태 유실까지 복구하려면 `equipment_status_log` 같은 이력 테이블이 선행되어야 하고,
그 시점에는 도메인 공통 시퀀스를 다시 검토하는 것이 맞다.
이번 설계는 **알람 전달 보장**으로 범위를 한정한다.

## 설계

### 1. 이벤트에 복구 기준 식별자 노출

`NewAlarmEvent` 가 이미 `data.id` 를 포함하고 있으므로, 클라이언트는 수신한 최대 id 를 기억한다.

### 2. 누락분 재조회 API

```
GET /api/v1/alarms?sinceId={lastReceivedId}&limit={n}
```

- `sinceId` 보다 큰 id 의 알람을 오래된 순으로 반환한다
- 기존 `level` / `resolved` 필터와 함께 사용할 수 있다
- **반환 개수에 상한을 둔다.** 연결이 끊긴 시간이 길면 수천 건이 쌓일 수 있고,
  상한이 없으면 복구 요청 한 번이 서버와 클라이언트 양쪽에 부담이 된다

### 3. 클라이언트 복구 흐름

```
연결 수립
  │
  ├─ 최초 연결 ──→ 알람 목록 전체 조회 (기존 동작)
  │
  └─ 재연결 ────→ GET /alarms?sinceId={마지막 수신 id}
                    │
                    └─→ 누락분을 수신 목록에 병합
```

재연결 판별이 필요하므로 연결 성공 횟수를 구분한다.
`reconnectDelay` 를 명시하고 **지수 백오프**를 적용한다 —
고정 간격이면 서버 재시작 시 모든 클라이언트가 같은 주기로 재접속을 시도한다.
`onWebSocketError` / `onStompError` 를 연결해 실패를 관측 가능하게 한다.

### 4. 수신 상태를 누적 구조로 변경 (L-3)

단일 값에서 배열 누적으로 바꾼다.
무한 증가를 막기 위해 보관 개수에 상한을 두고, 초과분은 오래된 것부터 버린다
(화면에 필요한 것은 최근 알람이고, 전체 이력은 REST 조회가 담당한다).

### 5. 중복 제거 (필수 후속)

복구 조회와 실시간 수신은 **반드시 겹친다.**
`sinceId=100` 으로 조회하는 동안 101번 알람이 실시간 경로로도 도착하면 중복이다.

이는 구현 실수가 아니라 재전달을 도입하면 발생하는 구조적 성질이다.
전달 보장을 at-least-once 로 설계하면 중복이 생기고, 중복 제거는 수신 측 책임이 된다.
(exactly-once 를 얻으려면 전달 단계가 아니라 **처리 단계의 멱등성**으로 해결해야 한다.)

따라서 수신 목록을 id 기준으로 dedupe 한다.

## 검증 방법

설계가 동작함을 주장이 아니라 테스트로 확인한다.

| 검증 항목 | 방법 |
|---|---|
| L-1 유실 재현 | 구독 해제 → 알람 생성 → 재구독 시 미수신 확인 (수정 전 기준선) |
| L-1 복구 | 같은 시나리오에서 재연결 후 해당 알람이 수신됨 |
| 재조회 쿼리 | `sinceId` 보다 큰 id 만, 오래된 순으로, 상한 이내로 반환 |
| L-3 | 연속 2건 도착 시 둘 다 유지됨 |
| 중복 제거 | 복구 경로와 실시간 경로로 같은 알람이 와도 1건만 표시 |

유실 재현 테스트를 먼저 작성해 **수정 전에 실패하는 것**을 확인한다.
그렇지 않으면 수정이 효과가 있었는지 판단할 근거가 없다.

Repository 조회는 실제 PostgreSQL 에 대해 검증한다 —
인메모리 DB 와 운영 DB 의 동작 차이로 쿼리 검증이 무의미해지는 것을 피한다.

## 범위 밖

| 항목 | 이유 |
|---|---|
| L-4 (저장·발행 원자성) | 발생 조건과 해결 방식이 다름. 별도 과제 |
| 설비 상태 이벤트 복구 | 이력 테이블이 선행되어야 함 |
| 외부 STOMP 브로커 도입 | 다중 서버 운영 시점에 재검토 |
| 전달 확인(ack) 기반 재전송 | DB 재조회로 동일 목적을 달성하므로 불필요 |
